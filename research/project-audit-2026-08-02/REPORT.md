# 医疗 Agent 项目实现审计、最新研究与全量优化方向

生成日期：2026-08-02  
范围：当前仓库实现、已有评测产物、2026-01-01 至 2026-08-02 的重点研究与监管动态  
结论性质：工程与研究审计，不构成临床有效性、法规合规或可部署性认证

## 一、执行摘要

1. **当前实现具备扎实的证据链 MVP 骨架**：任务 DAG、多查询检索、RRF、可选向量检索/外部重排、P#/K# 引用、主张验证、失败修复、风险路由、报告和 SSE Web 界面均已落地；151 个单元测试全部通过。
2. **最高优先级问题是评测语义错位**：PubMedQA 的最终 `yes/no/maybe` 标签在工作流结束后另行生成，没有进入主张验证器；因此“引用覆盖率/支持率接近满分”不能代表最终答案正确。495 例中最终标签总体正确率仅 36.57%，而验证器 2,567 个判定中 98.17% 为 `SUPPORTED`、0 个 `CONTRADICTED`，两者严重脱节。
3. **第二个 P0 是运行可靠性**：495 例中 118 例报错（23.84%），其中 116 例为模型供应商错误；完成病例的 p95 延迟为 347.7 秒。当前模型客户端缺少有界重试、指数退避与抖动、总截止时间、熔断和降级。
4. **第三个 P0 是验证器校准和证据粒度**：当前语义裁判给整个主张一个 verdict，再把同一关系复制到所有引用边；证据只保存粗粒度 chunk，页面、表格、bbox、精确 span 等契约字段尚未在主流程中兑现。需要建立专家金标的 claim–span 级评测，并把最终答案本身纳入验证。
5. **距离临床或真实患者部署仍有实质性差距**：最新研究一致指出，静态公开数据集上的正确率不足以证明长程任务、动态鲁棒性、工具执行、安全拒答、人类监督和外部有效性。项目应先进入“可靠离线评测 → 对抗测试 → 临床影子模式”，而不是直接开放诊疗建议。

## 三、当前实现评估

### 已完成且值得保留的设计

| 能力 | 当前实现 | 判断 |
|---|---|---|
| 工作流 | 规划—检索—抽取—综合的 DAG；失败任务及后继可修复 | 结构清晰，适合作为可观测执行骨架 |
| 证据链 | Evidence、Claim、SupportEdge 契约；P#/K# 引用约束 | 方向正确，但运行时粒度和验证语义仍不足 |
| 检索 | 多查询、词法候选、RRF、可选 FAISS/重排器 | 已超过单次向量检索，但还不是严格的混合检索 |
| 治理 | 来源类型、来源日期、版本/URL 元数据；高风险来源策略 | 有最小来源治理，需要扩展到内容安全和生命周期 |
| 风险 | answer / ask_clarification / defer / emergency_escalation | 有闭环入口，但阈值尚未按任务危害与校准数据设定 |
| 可观测性 | 图、报告、事件流、成本字段 | 可用于继续建设逐跳诊断和生产 SLO |
| 测试 | 151 个单测全部通过 | 对确定性逻辑覆盖良好；缺端到端浏览器、负载、故障注入和临床金标 |

### 实现层关键缺口

1. `dataset_evaluation.py` 在工作流之后另行生成 benchmark 标签，且没有把这个最终答案送回工作流验证器；`case_result.quality` 仍描述之前的工作流主张。
2. `evaluator.py` 的语义裁判输出一个主张级关系，再将相同关系和分数赋给每个引用证据；无法识别“一个引用支持、另一个引用无关/矛盾”。缓存键也没有纳入证据内容版本、裁判模型和 rubric 版本。
3. `evidence.py` 主要生成 chunk 级 `span_start=0/span_end=len`；契约中已有 page、bbox、table 等字段，但未形成稳定的 PDF/表格/网页精确定位链路。
4. `retrieval/state.py` 与 `agent_pipeline.py` 主要按“相关候选数量”停止，`missing_aspects` 尚未真正驱动检索；没有按主张槽位、反例、冲突和来源独立性判断证据充分性。
5. `vector.py` 使用向量结果替代词法排序，而非学习或校准后的稀疏—稠密融合；固定字符切块会割裂医学实体、表格和章节语义。
6. `openai_client.py` 单次请求失败即抛错，缺少面向 408/429/5xx/网络瞬断的幂等重试、退避抖动、截止时间、熔断和阶段级降级。
7. 规划器非法输出会直接 `plan_rejected`，没有有限重试、结构修复或保守的确定性计划模板。
8. 风险路由没有建立“任务危害 × 证据覆盖 × 不确定性 × 患者信息缺失 × 冲突”的可校准风险分数，也不支持“只回答低风险部分”的部分回答策略。
9. 尚未看到 FHIR、SNOMED CT、LOINC、ICD、药物相互作用库或临床计算器的确定性工具端口；数值/结构化任务仍主要依赖文本生成。
10. 知识导入缺少提示注入、文档投毒、AI 生成文本、撤稿/更新、签名与内容哈希谱系的主动检测。
11. 对外部署层尚缺正式的认证授权、TLS、PHI 脱敏/最小化、数据保留/删除、审计角色和事件响应闭环。
12. 工程层缺依赖锁文件和浏览器端到端测试；还应补齐静态类型、覆盖率/变异测试、负载/混沌测试与多 Python 版本矩阵。

## 四、真实评测重新解读

来源：`data/evaluation/reports/pubmedqa-test-500-agent-v2-chunks` 中 99 个非 legacy 报告、495 个病例；缺少编号 245–249。

| 指标 | 结果 | 解读 |
|---|---:|---|
| passed / needs review / plan rejected / error | 319 / 52 / 6 / 118 | 错误率 23.84%，不能只在成功病例上报告质量 |
| 最终标签解析覆盖率 | 366/495 = 73.94% | 约四分之一没有形成可评分答案 |
| 已解析答案准确率 | 181/366 = 49.45% | 只看解析成功病例仍接近随机基线风险区 |
| 全体病例总体准确率 | 181/495 = 36.57% | 更适合作为当前端到端基线 |
| 验证器 SUPPORTED | 2,520/2,567 = 98.17% | 与最终答案准确率严重不一致，说明验证对象/口径错误或校准失真 |
| PARTIAL / INSUFFICIENT / CONTRADICTED | 11 / 36 / 0 | 0 个矛盾判定是需要重点排查的分布异常 |
| 完成病例延迟 p50 / p95 / p99 | 91.2 / 347.7 / 704.9 秒 | 当前交互延迟不可接受，且长尾非常重 |
| 模型调用 / 总 token | 3,002 / 3,577,357 | 需要按阶段做成本—价值消融和预算控制 |
| 外部重排 / embedding 调用 | 755 / 1,488 | 应结合检索增益、失败率和延迟一起评估 |

标签混淆的主要模式是 `yes → maybe` 89 例和 `no → maybe` 59 例，显示系统大量回避明确结论；但这既可能是安全倾向，也可能是证据不足、标签提示、最终综合或解析协议的问题，必须通过病例级错误分类而不是只调 prompt 判断。

## 六、优化方向全景图

以下覆盖算法、系统、安全、临床、产品、工程和治理；“P0”是继续扩大功能前必须完成，“P1”是形成可信试点的条件，“P2”是规模化和临床研究条件。

### P0：先让评测、可靠性和安全判断可信

| # | 优化方向 | 具体改动 | 验收信号 |
|---:|---|---|---|
| 1 | 端到端答案验证 | 把最终回答/benchmark 标签建模为一等 Claim；与其直接证据一起进入 evaluator；所有错误和拒答保留在分母；区分事实主张、建议、结论和免责声明 | 最终答案覆盖率、总体准确率、选择性风险、claim–span F1 可独立复现；不再用中间主张的 citation 指标代替最终正确性 |
| 2 | 模型调用可靠性 | 对幂等的 408/429/5xx/连接瞬断做有界指数退避+jitter；总 deadline、阶段 timeout、熔断、供应商/模型降级、请求幂等键、可恢复 checkpoint | 供应商导致的病例失败率 <1%；重试不会重复副作用；错误类型和重试成本可观测 |
| 3 | 规划容错 | 对 schema 错误做一次结构修复和有限重试；失败后进入保守模板计划；将 planner 输出版本化 | `plan_rejected` <0.5%；模板计划在核心问答上保持安全可用 |
| 4 | claim–span 级验证器 | 每条 SupportEdge 单独判定 entail/partial/contradict/irrelevant；引用窗口包含精确原文和上下文；独立裁判模型；缓存键纳入证据哈希、rubric 和模型版本 | 300–500 条专家双标金集；不支持主张召回 ≥0.90、精度 ≥0.80；校准曲线和置信区间稳定 |
| 5 | 校准拒答与部分回答 | 以任务危害、证据覆盖、冲突、患者缺失字段和模型不确定性形成风险分数；允许回答低风险部分并明确未回答项 | 分风险层 risk–coverage 曲线；高危不安全回答召回 ≥0.95；拒答率不过度挤压低危可答覆盖 |
| 6 | 动态红队与知识安全 | 文档指令隔离、提示注入/投毒语料、AI 生成文本、错误高权威来源、时间漂移、隐私诱导、偏见改写；高风险时启用来源留一法/反事实检查 | 关键注入/投毒用例无越权行为；安全回归集持续运行；攻击检测的误报/漏报有金标 |

### P1：把证据和长程执行做实

| # | 优化方向 | 具体改动 | 验收信号 |
|---:|---|---|---|
| 7 | 真正的混合检索 | BM25/稀疏 + dense + 医学实体/术语 + 元数据过滤；按查询类型融合；不要让 FAISS 简单替换词法结果 | 按疾病、药物、指南、数值、否定句分桶的 Recall@20、nDCG、答案效用均优于当前基线 |
| 8 | 分层切块与结构解析 | 句子/表格/章节小检索单元，父级扩展上下文；PDF 页码、bbox、表格单元、网页段落锚点；OCR 质量分 | 引用可跳转到精确证据；表格/数值/否定信息的召回和定位准确率显著提升 |
| 9 | 证据充分性停止条件 | 从候选数量改为主张槽位覆盖；强制检索反例、独立来源和冲突；`missing_aspects` 驱动下一轮查询 | 减少“候选很多但关键问题未覆盖”；在相同准确率下调用数下降，或同等成本下准确率上升 |

## 七、建议路线图

### 0–2 周：修正基线

1. 将最终答案纳入 evaluator，重新定义聚合报表并补跑缺失 245–249。
2. 给模型客户端加有界重试、deadline、错误分类和熔断；规划器加结构修复与模板降级。
3. 固化 495/500 病例的病例级错误表：检索、证据、推理、标签、解析、工具/供应商、风险路由分层归因。
4. 加依赖锁、浏览器 smoke E2E 和 CI 中的最小离线回归。

### 3–6 周：让证据判断可校准

1. 建立 300–500 条 claim–span 双人标注金集，含支持、部分支持、矛盾、无关、时间失效和数值错误。
2. 实现 per-edge verifier、精确 span 和层级 chunk；完成 BM25+dense+实体的消融。
3. 建立任务危害分层和 risk–coverage 曲线，加入部分回答及强制反例检索。
4. 建投毒、提示注入、隐私、偏见、时间漂移与来源冲突红队集。

### 7–12 周：长程任务和可信试点

1. 上线只读 FHIR/术语/计算器工具沙箱，所有参数和结果均可追溯。
2. 加多轮、动态、工具执行和中文亚组评测；逐跳诊断、成本和 p95 SLO 进入发布门。
3. 完成审阅界面、覆盖/暂停/升级机制、事件日志和安全运营流程。
4. 完成数据流图、威胁模型、RBAC、PHI 策略、依赖与发布供应链。

### 12 周以后：临床证据而非演示指标

在锁定 intended use 后开展回顾性外部验证、静默影子运行和预先注册的前瞻研究；同时建立模型/知识更新后的变更控制与持续安全监测。没有完成这些步骤前，不应把当前结果表述为临床有效或可自主诊疗。

## 八、建议的发布门

1. **可靠性门**：供应商/网络导致的端到端失败 <1%，`plan_rejected` <0.5%，断点恢复无重复副作用。
2. **质量门**：最终答案覆盖率 ≥99%；准确性、拒答和错误严重度均以全部病例为分母并给出 95% CI；对 champion 基线做非劣/优效比较。
3. **证据门**：claim–span 不支持主张召回 ≥0.90、精度 ≥0.80；高危主张必须有至少一个合格来源且无未解决冲突。
4. **安全门**：高危不安全回答的检测/升级召回 ≥0.95；关键提示注入、投毒、隐私外泄测试不得出现成功攻击。
5. **性能门**：常规无修复问答 p95 初始目标 <30 秒；长程任务另设 SLO，且必须同时报告成本与成功率。
6. **治理门**：单病例可重建模型、提示、rubric、检索器、知识版本和原始证据；审阅、覆盖、事件和回滚均有责任人。

## 十、限制与不确定性

- 本报告是截至 2026-08-02 的定向深度检索，不是 PRISMA 系统综述；最新 arXiv 预印本尚未同行评审。
- PubMedQA 聚合基于仓库已有 495 个结果，缺少病例 245–249；不同模型/供应商配置混用的风险应通过报告中的配置字段进一步核对。
- 当前单测通过证明软件约束在测试范围内成立，不证明医学正确性、安全性或泛化能力。
- 建议阈值是启动工程门槛，最终数值应由 intended use、危害分析、临床专家和法规路径共同确定。

## 十一、最终判断

项目已经越过“只有提示词的 demo”阶段，最有价值的资产是明确的数据契约、证据链、可修复 DAG、风险出口和较好的单元测试基础。下一阶段不应继续以增加更多 Agent 角色或更长提示词为主，而应把资源集中在四件事：**最终答案进入验证闭环、供应商失败降到可控水平、claim–span 验证器用专家金标校准、风险/拒答在动态场景中可测量**。完成这四项后，再投资混合检索、FHIR 工具和临床试点，收益会更可验证，也更安全。
